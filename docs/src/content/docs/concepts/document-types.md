title: Document Types
description: Understanding document type abstractions in AeroDB

AeroDB supports three document type models, each suited to different levels of abstraction. You can mix all three in a single store.

## Record / IRecord / RecordId

At the lowest level, SurrealDB identifies every row by a `table:id` record ID. The official .NET SDK provides the `IRecord` interface and `Record` base class in `SurrealDb.Net.Models`:

```csharp
public interface IRecord
{
    RecordId? Id { get; set; }
}

public abstract class Record : IRecord
{
    public RecordId? Id { get; set; }
}
```

`RecordId` carries both the table name and the id portion (e.g., `"user"` and `185473209184321536`). The typed variant `RecordIdOf<TId>` enforces the id type at compile time:

```csharp
// Typed record ID
var rid = RecordId.From("user", 185473209184321536L);        // RecordIdOf<long>
var sid = RecordId.From<Guid>("session", Guid.NewGuid());     // RecordIdOf<Guid>
var sid = RecordId.From("product", "SKU-123");                // RecordIdOfString
```

Use the `Record` base class when you need direct access to `RecordId` — typically in edge definitions, graph queries, or when interoperating with raw SurrealQL results.

```csharp
public class Membership : EdgeRecord
{
    public string Role { get; set; }
}

// EdgeRecord inherits Record, so Id is RecordId?
// In/Out are RelationRecord properties pointing to the connected records
```

`Record` subclasses are required for polymorphic document hierarchies, graph edges, and SurrealDB-native features like live queries with raw record IDs.

## IEntity\<TId\>

`IEntity<TId>` is AeroDB's primary abstraction for domain entities with a typed primary key. It decouples your domain model from SurrealDB's `RecordId` type:

```csharp
public interface IEntity<TId>
    where TId : notnull, IEquatable<TId>, IComparable<TId>
{
    TId Id { get; set; }
}
```

AeroDB translates between `TId` and SurrealDB's `RecordId` transparently. When you store an entity with `Id = 42`, it creates `user:42` in the database. When loading, it parses the record ID and writes the numeric portion back to the `Id` property.

The `Entity<TId>` base class implements the interface with a simple auto-property:

```csharp
public abstract class Entity<TId> : IEntity<TId>
    where TId : notnull, IEquatable<TId>, IComparable<TId>
{
    public TId Id { get; set; } = default!;
}
```

### IEntity\<long\> — Snowflake IDs (Most Common)

The recommended default. Use `EntitySnowlake` (aliases `Entity<long>` with Snowflake auto-generation):

```csharp
public class User : EntitySnowlake
{
    public string Name { get; set; }
    public string Email { get; set; }
}

// Equivalent:
public class User : Entity<long>
{
    public User() => Id = SnowflakeGenerator.NewId();
    // ...
}
```

Snowflake IDs are distributed, time-sortable 64-bit integers generated by the FlakeId library. They perform well as SurrealDB record IDs and enable efficient range queries.

### IEntity\<Guid\>

Use `EntityGuid` for globally unique identifiers, common when integrating with external systems or when GUID semantics are required:

```csharp
public class Product : EntityGuid
{
    public string Sku { get; set; }
    public decimal Price { get; set; }
}

// Or explicit:
public class Product : IEntity<Guid>
{
    public Guid Id { get; set; } = Guid.NewGuid();
    public string Sku { get; set; }
}
```

### IEntity\<string\>

Use `EntityString` for domain-specific identifiers (email addresses, slugs, external keys):

```csharp
public class Tenant : EntityString
{
    public string DisplayName { get; set; }
}
```

### Convenience Base Classes

| Class | Id Type | Generation |
|-------|---------|------------|
| `EntitySnowlake` | `long` | `SnowflakeGenerator.NewId()` |
| `EntityString` | `string` | `SnowflakeGenerator.NewId().ToString()` |
| `EntityInt` | `int` | `Random.Next(1, int.MaxValue)` |
| `EntityGuid` | `Guid` | `Guid.NewGuid()` |
| `Entity<TId>` | Generic | None (you must set `Id`) |

## POCOs

AeroDB supports plain CLR objects with no interface requirement. Any class can be used as a document — there is no mandatory `IRecord` or `IEntity<TId>` constraint:

```csharp
public class AuditLog
{
    public long Id { get; set; }   // auto-detected as identity
    public string Action { get; set; }
    public string Details { get; set; }
}
```

**Convention-based identity discovery:**
- A property named `Id` (case-insensitive) is automatically treated as the primary key
- The identity property type must match one of the supported key types (`long`, `int`, `ulong`, `uint`, `string`, `Guid`, `byte`, `short`, `DateTime`)
- For types without a conventional `Id` property, you must explicitly configure the identity:

```csharp
opts.Schema.For<ExternalEvent>()
    .Identity(x => x.EventId);  // explicit identity property
```

**When POCOs are the right choice:**
- **Integration / migration** — porting an existing codebase without modifying domain classes
- **Read models** — denormalized projections that don't need write-back
- **Event store payloads** — event data objects that are never loaded by primary key
- **Simple value documents** — configuration entries, lookup tables, reference data

## Choosing a Document Type

| Approach | Interface | Identity | Best For |
|----------|-----------|----------|----------|
| `Record` (SurrealDB) | `IRecord` | `RecordId?` | Edges, graph queries, raw SurrealQL |
| `IEntity<TId>` | `IEntity<TId>` | `TId` | Domain entities, primary-key access |
| POCO | None | Convention | Read models, events, quick integration |

You can freely mix all three in the same store. AeroDB detects the pattern at registration time and applies the appropriate identity mapping and serialization strategy:

```csharp
// Record subclass — RecordId identity
public class LogEntry : Record { }

// IEntity<long> — Snowflake identity
public class User : EntitySnowlake { }

// POCO — convention-based Id property
public class Settings
{
    public long Id { get; set; }
    public string Theme { get; set; }
}
```
